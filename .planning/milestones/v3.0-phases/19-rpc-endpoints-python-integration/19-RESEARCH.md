# Phase 19: RPC Endpoints & Python Integration - Research

**Researched:** 2026-03-30
**Domain:** Twirp RPC endpoints for TradeSignal write/query + Python datasource pattern
**Confidence:** HIGH

## Summary

Phase 19 adds three new Twirp RPC endpoints (WriteSignal, GetSignals, GetProcessedSignals) to the existing PlaygroundService and creates the Python datasource script skeleton in `src/clients/python/datasources/`. All code patterns are already established in the codebase -- this phase follows existing Twirp handler conventions, proto generation workflow, and OTel telemetry patterns exactly.

The key architectural insight is that signals are GLOBAL events (D-01). WriteSignal has no playground_id -- it writes to a global ISignalRepository accessible from the Server struct. GetProcessedSignals reads per-playground consumed signals (from the playground's own signalRepo). GetSignals reads from the global store with optional filters.

**Primary recommendation:** Follow the exact handler pattern in `grpc.go`, add proto messages to `playground.proto`, run `task gen:proto`, then implement handlers. The Python side is auto-generated stubs + a thin wrapper in the client + a datasource skeleton directory.

## Architecture Patterns

### Signal Storage Architecture

The Server struct currently holds `dbService` which contains all playgrounds. For global signal storage, the Server needs a **global signal repository** separate from per-playground repos.

**Current state:**
- Each `Playground` has its own `signalRepo ISignalRepository` (set via `SetSignalRepo()`)
- `InMemorySignalRepository` provides sorted, cursor-based, clock-gated delivery
- On `SavePlayground`, signals are batch-persisted to ESDB via `PublishAndSaveEvent`

**Phase 19 addition:**
- Server gets a new field: `globalSignalRepo ISignalRepository` (an `InMemorySignalRepository`)
- `WriteSignal` writes to this global repo
- `GetSignals` reads from this global repo with filters
- `GetProcessedSignals` reads from a specific playground's signalRepo (already delivered signals)
- Per-playground signalRepos continue to get signals via `NextTick` clock-gating (existing Phase 18 mechanism)

**Key flow for connecting global to per-playground:**
WriteSignal writes to globalSignalRepo. When a playground calls NextTick, the playground's own signalRepo delivers clock-gated signals. The bridge between global and per-playground is NOT this phase's responsibility -- that is the existing Phase 18 mechanism where signals are written to a playground's repo by the caller (Python or the sim loop). Phase 19 just provides the RPC surface.

### Proto Message Design (Claude's Discretion)

```protobuf
// WriteSignal: global signal production (no playground_id per D-01)
message WriteSignalRequest {
    string name = 1;           // SignalName (validated server-side)
    string symbol = 2;         // StockSymbol
    google.protobuf.Timestamp timestamp = 3;
    map<string, string> attributes = 4;  // matches existing proto convention
}

message WriteSignalResponse {
    string signal_id = 1;      // UUID generated by Go server
}

// GetSignals: global signal query
message GetSignalsRequest {
    optional string name = 1;
    optional string symbol = 2;
    optional google.protobuf.Timestamp from_timestamp = 3;
    optional google.protobuf.Timestamp to_timestamp = 4;
}

message GetSignalsResponse {
    repeated TradeSignalProto signals = 1;
}

// GetProcessedSignals: per-playground consumed signals (RPC-01)
message GetProcessedSignalsRequest {
    string playground_id = 1;
    optional string name = 2;
    optional string symbol = 3;
    optional google.protobuf.Timestamp from_timestamp = 4;
    optional google.protobuf.Timestamp to_timestamp = 5;
}

message GetProcessedSignalsResponse {
    repeated TradeSignalProto signals = 1;
}
```

Note: `TradeSignalProto` already exists in the proto file (used in TickDelta.new_signals).

### Existing RPC Handler Pattern

Every handler in `grpc.go` follows this exact pattern:
1. Parse request (validate UUIDs, parse enums)
2. Call `s.dbService.GetPlayground(id)` if playground-scoped
3. Perform business logic
4. Convert domain objects to proto messages
5. Return proto response

For WriteSignal (no playground_id), the pattern simplifies to:
1. Validate signal name via `SignalName.Validate()`
2. Create `TradeSignal` via `NewTradeSignal()`
3. Write to `s.globalSignalRepo`
4. Increment OTel counter
5. Return `WriteSignalResponse{signal_id: signal.ID.String()}`

### Signal Name Validation

`SignalName.Validate()` currently only validates 4 names: `ma_crossover`, `start_of_week`, `covered_call`, `mean_reversion`. The older constants (supertrend, stochastic_rsi) are NOT validated. WriteSignal should use `Validate()` but this may need expanding as new datasources are added. For Phase 19 (skeleton only, no example datasources), the existing validation is sufficient.

### Python Datasource Skeleton Pattern

```
src/clients/python/datasources/
    __init__.py          # Package marker + produce_signals protocol doc
    base_datasource.py   # Optional: base class or protocol definition
```

Each future datasource module will follow this dual-mode pattern:
- **Live mode**: `python -m datasources.ma_crossover` calls WriteSignal RPC
- **Sim mode**: `from datasources.ma_crossover import produce_signals` (direct import, no RPC)

The `produce_signals()` function signature returns a list of signal dicts. In live mode, `__main__` iterates and calls WriteSignal via the Twirp client.

However, since WriteSignal is global (not playground-scoped), it might be more appropriate to add it as a standalone function or on a separate lightweight client class. The auto-generated `PlaygroundServiceClient.WriteSignal()` method will be available after proto regeneration.

**Recommendation:** Add a standalone `SignalClient` class or add `write_signal()` as a classmethod/staticmethod since it doesn't need playground state. Alternatively, keep it on `BacktesterPlaygroundClient` for convenience since it already holds the Twirp client instance.

### OTel Telemetry Pattern

Existing telemetry in `src/go/telemetry/metrics.go` follows a clear pattern:
- Counters declared as package-level vars
- Initialized in `Init()` via `otel.GetMeterProvider().Meter("grodt")`
- Used with nil-check: `if telemetry.SignalsProduced != nil { ... }`
- Attributes via `metric.WithAttributes(attribute.String(...))`

**New counters (D-06):**

```go
var (
    SignalsProduced metric.Int64Counter  // grodt.signals.produced
    SignalsConsumed metric.Int64Counter  // grodt.signals.consumed

```

Note: `SignalsGenerated` already exists (used by RecordSignal). The new `SignalsProduced` is distinct -- it counts TradeSignal events via WriteSignal RPC, while `SignalsGenerated` counts the older RecordSignal telemetry events.

Attributes for SignalsProduced: `signal_name`, `symbol`
Attributes for SignalsConsumed: `playground_id`, `signal_name`, `client_id`

### Proto Generation Workflow

```bash
task gen:proto
```

This generates:
- Go: `src/go/playground/playground.pb.go`, `playground.twirp.go`
- Python: `src/clients/python/rpc/playground_pb2.py`, `playground_twirp.py`

After adding new RPC methods and messages to `playground.proto`, running `task gen:proto` auto-generates both Go and Python stubs. The Python `PlaygroundServiceClient` will automatically get `WriteSignal()`, `GetSignals()`, and `GetProcessedSignals()` methods.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Proto message serialization | Custom JSON encoding | protoc + twirpy codegen (`task gen:proto`) | Auto-generates type-safe Go + Python stubs |
| UUID generation | Custom ID scheme | `github.com/google/uuid` (already used) | Consistent with existing playground/order IDs |
| Signal sorted storage | Custom sorted list | `InMemorySignalRepository` (already built) | Binary search insertion, cursor delivery, thread-safe |
| OTel counter creation | Manual metric plumbing | `telemetry.Init()` pattern (add new vars) | Consistent with existing counters |
| Python Twirp client | Manual HTTP calls | Auto-generated `PlaygroundServiceClient` | `task gen:proto` generates it |

## Common Pitfalls

### Pitfall 1: Forgetting to run task gen:proto
**What goes wrong:** Adding RPC methods to proto but forgetting to regenerate stubs causes compile errors or missing Python methods.
**Why it happens:** Proto file edit and stub generation are separate steps.
**How to avoid:** Always run `task gen:proto` immediately after editing `playground.proto`. Verify both Go and Python stubs are updated.
**Warning signs:** Go build errors about unimplemented interface methods; Python `AttributeError` on client methods.

### Pitfall 2: SignalName validation is restrictive
**What goes wrong:** WriteSignal rejects signal names not in the `Validate()` switch statement.
**Why it happens:** `Validate()` only allows 4 signal names. New datasources need new names registered.
**How to avoid:** Either expand `Validate()` to accept all known names, or make WriteSignal accept any string and do soft validation (log warning, don't reject). Recommendation: keep strict validation but document that adding a new datasource requires adding a SignalName constant.
**Warning signs:** WriteSignal returns error for valid-seeming signal names.

### Pitfall 3: Global vs per-playground signal confusion
**What goes wrong:** Trying to read global signals via GetProcessedSignals or vice versa.
**Why it happens:** Two different repositories serve two different purposes.
**How to avoid:** Clear naming: `globalSignalRepo` on Server vs `playground.GetSignalRepo()` per playground. GetSignals reads global; GetProcessedSignals reads per-playground.
**Warning signs:** GetProcessedSignals returns empty when signals have been written but playground hasn't ticked.

### Pitfall 4: Attributes type mismatch (map[string]interface{} vs map[string]string)
**What goes wrong:** Go domain uses `map[string]interface{}` but proto uses `map<string, string>`.
**Why it happens:** Proto3 doesn't support `interface{}` / `Any` in maps efficiently.
**How to avoid:** Convert at the RPC boundary using `fmt.Sprintf("%v", v)` for outgoing and parse strings back for incoming. This pattern is already used in the NextTick signal serialization (line 955-958 of grpc.go).
**Warning signs:** Type assertion panics when reading attributes.

### Pitfall 5: Python import path for datasources
**What goes wrong:** `from datasources.x import produce_signals` fails because Python path isn't set up.
**Why it happens:** Python scripts run from `src/clients/python/` and need the directory in sys.path.
**How to avoid:** Ensure `datasources/` has `__init__.py` and that scripts are run from the correct working directory. The existing pattern (running from `src/clients/python/`) should work since `datasources/` will be a sibling of `engine/` and `rpc/`.
**Warning signs:** `ModuleNotFoundError: No module named 'datasources'`.

## Open Questions

1. **Global-to-playground signal bridge**
   - What we know: WriteSignal writes to global repo. Playgrounds have their own repos for clock-gated delivery.
   - What's unclear: Who copies signals from global repo to playground repos? In sim mode, Python writes signals directly to playground's repo via the existing mechanism. In live mode, the bridge may need a subscription mechanism.
   - Recommendation: For Phase 19, the bridge is NOT required. WriteSignal stores globally; GetSignals reads globally. Per-playground delivery continues via existing Phase 18 mechanism (Python writes to playground repo during tick loop). The bridge is a Phase 20+ concern.

2. **RecordSignal deprecation timeline**
   - What we know: RecordSignal is a telemetry-only endpoint. WriteSignal replaces its function with actual domain signal creation.
   - What's unclear: Should RecordSignal be deprecated in Phase 19 or left until strategies are migrated?
   - Recommendation: Leave RecordSignal as-is. Add a code comment marking it for deprecation. Remove when strategies migrate (Phase 21-22).
