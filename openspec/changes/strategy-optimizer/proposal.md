# Strategy Optimizer (recommendation-only parameter proposals from sim outcomes)

## Why

The architecture doc's Strategy Optimizer closes the fast feedback loop: accumulated `sim_outcomes` reveal *how* trades fail (stop churn, timeout drag, targets left on the table), and that evidence should drive proposed execution-parameter updates — stop %, target %, hold days. Today the outcome data and its trust gate (the shipped `optimizer-validation-pipeline`) exist, but nothing consumes them: no component turns EV/outcome history into actionable tuning, and there is no operator surface to see what the data recommends. This change builds the optimizer — deliberately as a **recommendation engine whose output requires operator action**, never a component that touches live trading configuration on its own.

## What Changes

- Add a **strategy optimizer** engine (new Go sub-package `src/go/tradingstack/stratopt/`) that generates candidate strategy-parameter proposals from historical sim outcomes, per `(strategy_id, regime)` group.
- **Validation-pipeline gating**: the optimizer consumes *only* outcomes that survive the already-shipped `optimizer-validation-pipeline` (timestamp audit, distribution check, regime-confidence filter, fidelity gate, EV-weight join). Rows dropped by any stage never influence a proposal; each surviving outcome carries its `ev_weight` into the optimizer's statistics.
- **Deterministic, rule-based candidate generation (v1)** — three rules lifted from the architecture doc's own diagnostics: dominant quick stop-outs among losses → propose widening the stop; dominant timeout losses → propose shortening max hold; dominant fast target hits among wins → propose raising the target. Each proposal is a bounded relative adjustment (fixed configured step) with full supporting evidence (weighted EV, exit-reason mix, sample counts, pipeline gating summary). Groups below a minimum decided-sample threshold (the candidate-generation pre-filter, default 50) produce no candidates. **The arch doc names Bayesian optimization; v1 is deterministic rules — flagged for sign-off**, see design.md D1.
- **Overfitting-gate verdict before review**: every generated proposal MUST obtain a verdict from the shared `overfitting-countermeasures` gate (`src/go/tradingstack/overfitting`, submitting as `proposal_kind = strategy` — the kind the gate's verdict table reserves for this optimizer) before it can enter the operator review queue. The optimizer constructs the gate's caller-supplied evidence from the same gated outcome rows the proposal was derived from: chronological walk-forward folds, in-sample vs out-of-sample performance for the retention check, a multiplier encoding of the proposed adjustment for the parameter-step check, and the out-of-sample dispersion inputs for the deflated t-statistic check. Gate thresholds are configurable per proposal kind; the optimizer supplies a strategy-kind gate configuration because per-`(strategy_id, regime)` groups are far thinner than scanner training data (design.md D7, defaults **flagged for sign-off**). A gate-rejected proposal is persisted with status `rejected_by_gate` — verdict attached, audit-visible — and never reaches the operator queue.
- **Proposals persist as recommendations**: a new additive `strategy_proposals` table (Postgres only, in-package migration following the `MigrateNetEvCostModel` precedent) with status vocabulary `rejected_by_gate | pending_review | accepted | dismissed` and a `verdict_id` column referencing the gate's persisted `overfitting_verdicts` row (the FK direction the gate's design specifies). The shared status core (`rejected_by_gate`, `pending_review`) matches `scanner-optimizer`; terminal states differ deliberately (`accepted|dismissed` here vs the scanner's `promoted|dismissed`) because the scanner has a real apply target and this optimizer does not — design.md D8. **Nothing auto-applies**: no code path reads a proposal to modify any strategy configuration, live/paper trading behavior, or order flow; accepting a proposal records the operator's decision and nothing else. Applying an accepted proposal to an actual strategy config is explicitly out of scope (no canonical strategy-config store exists yet — design.md D2).
- **Operator surface**: `task optimizer:propose` (generate; defaults to synthetic dry-run — prints, persists nothing, needs no DB), `task optimizer:proposals` (list; defaults to the `pending_review` queue, `rejected_by_gate` visible only via an explicit status filter), `task optimizer:proposal ID=<id>` (inspect with evidence and gate verdict), `task optimizer:proposal:decide ID=<id> DECISION=accepted|dismissed` (record a decision; only `pending_review` proposals are decidable).
- Autonomous-run safe by construction: no live/paper orders, DB writes confined to `strategy_proposals` plus the gate's own `overfitting_verdicts` (written through the gate's `VerdictStore`), synthetic mode as the default task invocation. Not BREAKING.

## Capabilities

### New Capabilities

- `strategy-optimizer`: pipeline-gated ingestion of sim outcomes, weighted per-group outcome statistics, the candidate-generation minimum-sample pre-filter, deterministic rule-based candidate generation, overfitting-gate evidence construction and verdict acquisition, and the run entry point with synthetic mode.
- `optimizer-proposals`: the `strategy_proposals` persistence model and migration (gate-aware status vocabulary, verdict reference), the recommendations-only / never-auto-applied invariant, and the operator list/inspect/decide surface.

### Modified Capabilities

(none — the optimizer consumes `optimizer-validation-pipeline` output via its existing `Result` contract, joined back to outcomes by `SimOutcomeID`, and consumes `overfitting-countermeasures` via its caller-supplied `Evidence`/`RunGate`/`VerdictStore` contract as designed; no shipped or sibling-drafted requirement changes)

## Impact

- **New code**: `src/go/tradingstack/stratopt/` (statistics, rules, generation, gate-evidence builder, proposal store, migration `MigrateStrategyOptimizer`, synthetic fixtures, tests); new command `cmd/strategy-optimizer/`; `taskfile.yml` gains the four targets above.
- **Database**: one new additive table `strategy_proposals` (with `verdict_id` referencing `overfitting_verdicts.id`); no change to the six trading-stack tables or any playground table. Verdict rows are written through the `overfitting-countermeasures` capability's own store and migration. Postgres only — no ESDB (ADR-0004 pending), no new infrastructure.
- **Dependencies**: `tradingstack` models, `optvalidation` (data-quality gate), `overfitting` (proposal honesty gate — new dependency on the sibling change's package), `gorm`, `google/uuid`, testcontainers for tests. Reads `scan_results`/`sim_outcomes` plus the pipeline's reference tables (`feature_distributions`, `simulator_fidelity`, `strategy_ev_weights`) for real runs.
- **Sequencing (hard dependency)**: **`overfitting-countermeasures` must land before `strategy-optimizer`** — this change imports its `Evidence`/`RunGate`/`VerdictStore` contract and its `strategy_proposals.verdict_id` references the gate's `overfitting_verdicts` table (the same ordering that change already establishes ahead of `scanner-optimizer`; the dependency points one way — the gate imports nothing from us). Additionally, this change benefits from `continuous-fidelity-monitoring` (real `simulator_fidelity` history feeding the pipeline's fidelity gate) but does not depend on it — the pipeline degrades gracefully with empty reference tables.
- **Not covered yet (explicit non-goals)**: Bayesian/search-based optimization over re-simulated candidates (needs batch re-simulation); applying accepted proposals to any strategy config (needs a strategy-config registry); the Scanner Optimizer (separate roadmap card); scheduling optimizer runs (operator-invoked for now); tuning the strategy-kind gate thresholds against live data (defaults are conservative starting points).
